# 输入分析

## 核心问题

产品需求进入开发时，最容易失控的点是：

- 需求没澄清就开始写代码。
- 不知道应该改哪个模块。
- 把局部需求做成过度复杂的新模块。
- 忽略数据、状态、接口和权限影响。
- 没有风险分级，导致高风险需求也被当成小改动处理。

因此，本能力的核心不是实现，而是开发前的架构翻译。

## 与前后工作流的关系

| 阶段 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `project-understanding-workflow.md` | 先知道项目当前结构。 |
| 当前 | `requirement-to-architecture-workflow.md` | 把需求映射到项目结构和架构影响。 |
| 后续 | `module-boundary-analysis-workflow.md` | 当模块职责不清或需要新增模块时使用。 |
| 后续 | `change-risk-assessment-workflow.md` | 当变更风险较高时使用。 |
| 后续 | `impact-analysis-workflow.md` | 输出更细的文件、接口、测试影响清单。 |
| 后续 | `implementation-workflow.md` | 影响范围和风险清楚后进入实现。 |

## 必须覆盖的能力

1. 需求清晰度判断。
2. 待确认问题。
3. 影响范围总览。
4. 模块变更建议。
5. 新增模块判断。
6. 数据与状态影响。
7. 接口与协作影响。
8. 风险等级。
9. 后续工作流建议。

## 设计结论

本工作流应输出“架构影响分析报告”，作为开发前的中间层产物。

它不能只复述需求，也不能直接写实现方案，而是要回答：

```text
这个需求会让项目哪里发生变化？
这些变化是否合理？
风险在哪里？
下一步应该怎么推进？
```

# 输出评审

## 总体结论

本次“已有项目理解工作流”可以作为 developer-kit 的第二个基础能力。

它补齐了新项目启动之后的另一个关键场景：当 AI 接手已有项目时，先建立上下文、模块边界和风险认知，再进入开发。

## 分项评分

参考 `11-evaluations/output-scorecards/project-understanding-scorecard.md`。

| 维度 | 分数 | 说明 |
| --- | --- | --- |
| 入口识别 | 5 | 覆盖 README、AGENTS、docs、Cursor rules、技术栈入口、源码和测试目录。 |
| 事实证据 | 5 | 明确要求区分事实、推断和待确认问题。 |
| 技术栈判断 | 5 | 覆盖语言、框架、启动、构建、测试、环境变量。 |
| 目录职责 | 5 | 要求解释目录职责，而不是只列目录。 |
| 模块地图 | 5 | 覆盖模块职责、输入、输出、依赖和风险。 |
| 协作链路 | 5 | 覆盖用户操作、页面、状态、API、数据和 UI 返回。 |
| 风险缺口 | 5 | 覆盖缺失文档、边界不清、测试缺口和高风险区域。 |
| 下一步建议 | 5 | 能连接到后续 developer-kit 工作流。 |

总分：40 / 40。

## 主要优点

- 能帮助用户快速建立已有项目全局观。
- 强制区分事实和推断，降低 AI 误判风险。
- 以模块边界和协作链路作为核心输出，不只是目录扫描。
- 能自然衔接后续需求到架构、模块边界、风险评估和实现执行。

## 需要注意

- 实际使用时应根据项目规模控制阅读深度，避免小任务过度分析。
- 对大型项目可以先输出一级理解报告，再选择重点模块深入。

## 是否建议提升为全局能力

建议提升。

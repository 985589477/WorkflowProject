# 输入分析

## 核心问题

项目长期维护中，依赖和技术债最容易被低估：

- AI 为了方便随手新增依赖。
- 临时方案没有标注，后来变成长期方案。
- 技术债只有抱怨，没有偿还计划。
- 依赖升级没有兼容性验证。
- 依赖风险没有进入 ADR 或文档。

因此，本能力要把“短期方便”和“长期成本”放在同一个判断框架里。

## 与前后工作流的关系

| 阶段 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `architecture-decision-record-workflow.md` | 高影响依赖选择需要 ADR。 |
| 前置 | `code-review-workflow.md` | 评审发现依赖风险或技术债。 |
| 当前 | `dependency-and-tech-debt-workflow.md` | 管理依赖、临时方案和技术债。 |
| 后续 | `implementation-workflow.md` | 执行依赖调整或债务偿还。 |
| 后续 | `testing-verification-workflow.md` | 验证依赖调整后的兼容性。 |
| 后续 | `documentation-sync-workflow.md` | 同步依赖说明和技术债记录。 |

## 必须覆盖的能力

1. 治理对象分类。
2. 必要性判断。
3. 备选方案。
4. 依赖风险评估。
5. 技术债记录。
6. 偿还计划。
7. 验证和回滚。
8. ADR 判断。
9. 后续跟踪。

## 设计结论

本工作流应输出“依赖与技术债治理报告”。

它要回答：

```text
这个依赖或技术债是否值得处理？
短期收益是什么？
长期成本是什么？
未来怎么还？
```

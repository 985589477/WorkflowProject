## 可复用经验

### 1. 角色能力建设完成后，需要导出层

`04-workflows/` 适合项目内部维护，`14-exports/` 适合外部使用。

如果没有导出层，用户在其他项目里会不知道该复制哪些文件，也容易把 WorkflowProject 内部目录结构带出去。

### 2. START-HERE 必须承担调度职责

入口文档不能只教用户怎么说话，还要告诉外部 AI：

- 什么时候触发能力包。
- 触发后先读什么。
- 如何判断任务类型。
- 如何选择 workflow、template 和 scorecard。
- 输出保存在哪里。

### 3. 开发能力包不能限制 Codex 或 Cursor

developer-kit 的作用不是替代 AI 开发能力，而是让 AI 的开发能力更可控。

它约束的是：

- 目标。
- 边界。
- 风险。
- 验收。
- 复盘。

不是约束 AI 只能机械执行文档。

### 4. 开发总入口必须是生命周期编排器

开发总入口不能只做“用户问题 -> 某个工作流”的分流。

真正有用的开发治理入口应该能持续推进：

```text
需求理解 -> 开发确认 -> 项目理解 -> 功能规划 -> 实现 -> 验证 -> 文档 -> 评审 -> 发布或复盘
```

每个阶段结束后都要判断下一阶段，不能因为完成一个分析文档就默认任务结束。

### 5. 实现前必须先整体规划

AI 直接写代码容易局部最优、破坏边界或遗漏验证。

进入实现前应先明确：

- 功能范围。
- 非范围。
- 模块协作。
- 影响文件。
- 实现顺序。
- 验证方式。
- 待确认问题。

### 6. 不明确时主动询问

当需求、范围、技术方案、验收标准或风险不明确时，应主动问用户。

这比自作主张更符合开发治理目标。

### 7. 导出包需要使用体验层

能力文件本身不等于好用。

导出包还需要：

- 首次接入说明。
- 快速启动示例。
- 执行状态格式。
- 任务结束标准。
- Codex 和 Cursor 的使用差异说明。

这些内容能降低外部项目使用成本，避免用户复制能力包后不知道怎么启动。

### 8. 开发实现阶段需要任务拆解和逐条执行

开发角色不应只在实现前给出笼统计划。

中高风险实现必须拆成开发任务列表，并按以下节奏推进：

```text
一次只执行一条任务
-> 完成本条任务的最小改动
-> 验证本条任务
-> 记录结果
-> 判断是否进入下一条任务
```

这能降低 AI 一次性大范围修改带来的失控风险。

### 9. 开发前必须检查项目规范

开发角色不能只理解目录和代码，还要先确认项目是否已经有设计规范、组件规范、交互规范、代码规范、测试规范和 AI 协作规则。

如果忽略这些规范，AI 很容易写出“功能能跑但风格不一致、边界不一致、测试方式不一致”的代码。

因此进入实现前应先检查：

```text
设计规范 / 组件规范 / 交互规范 / 视觉规范
代码风格 / 架构约束 / 目录约定 / 命名规范
测试规范 / 文档规范 / AI 协作规则
```

有规范就遵守；没有规范就说明缺失，并根据风险决定是否从现有代码归纳临时约定，或先询问用户补齐。

### 10. 开发角色需要覆盖真实协同缺口

开发角色不能只覆盖“需求到实现”的顺滑路径，还必须覆盖真实开发中最常见的复杂情况：

- 问题发生后先定位再修复。
- 数据、接口和状态不清时先定义契约。
- 权限、安全和敏感数据相关任务先做治理。
- 多个工作流之间允许插入、回退、跳过和暂停确认。

这四类能力可以显著提升 developer-kit 的协同灵活性，避免 AI 在上下文不完整时直接进入代码实现。

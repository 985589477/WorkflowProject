# 输入分析

## 核心问题

AI 协作开发的风险不只来自代码能力，而来自执行边界不清：

- 小改动和高风险变更使用同一种执行方式。
- 涉及数据、权限、支付、生产配置时没有提前确认。
- 批量修改、删除、迁移等危险操作被直接执行。
- 开发完成后没有验证和回滚准备。

因此，本能力需要成为“执行前闸门”。

## 与前后工作流的关系

| 阶段 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `requirement-to-architecture-workflow.md` | 提供需求影响范围。 |
| 前置 | `module-boundary-analysis-workflow.md` | 提供模块边界和协作判断。 |
| 当前 | `change-risk-assessment-workflow.md` | 判断风险等级和执行权限。 |
| 后续 | `impact-analysis-workflow.md` | 风险可控后进一步细化影响范围。 |
| 后续 | `implementation-workflow.md` | 满足执行条件后进入实现。 |

## 必须覆盖的能力

1. 变更目标摘要。
2. 影响对象识别。
3. 风险信号识别。
4. 风险等级判断。
5. AI 执行策略。
6. 人工确认问题。
7. 验证要求。
8. 回滚要求。
9. 后续工作流建议。

## 设计结论

本工作流应输出“变更风险评估报告”。

它要回答：

```text
这次变更风险多大？
AI 能不能直接做？
做之前需要确认什么？
做完以后怎么验证？
出问题如何回退？
```

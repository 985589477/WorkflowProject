# 输入分析

## 核心问题

AI 协作开发中，模块边界失控通常表现为：

- 新功能不知道放在哪里。
- 为了方便把逻辑塞进最近的文件。
- 模块越来越大，职责越来越混。
- 通用工具混入业务逻辑。
- 多个模块同时修改同一份状态。
- 不该依赖的模块形成反向依赖或循环依赖。
- 为了拆文件而过度新增模块。

因此，本能力必须回答：

```text
能力归谁管？
谁不能管？
谁调用谁？
数据和状态归谁？
是否真的需要新模块？
```

## 与前后工作流的关系

| 阶段 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `requirement-to-architecture-workflow.md` | 先知道需求影响哪些模块。 |
| 当前 | `module-boundary-analysis-workflow.md` | 进一步明确模块职责、边界和协作。 |
| 后续 | `change-risk-assessment-workflow.md` | 对边界调整、新增模块和跨模块协作做风险分级。 |
| 后续 | `impact-analysis-workflow.md` | 输出文件级影响范围。 |
| 后续 | `implementation-workflow.md` | 边界清楚后进入实现。 |

## 必须覆盖的能力

1. 分析对象确认。
2. 现有模块画像。
3. 职责归属判断。
4. 新增模块判断。
5. 目标模块边界。
6. 数据与状态归属。
7. 模块协作方式。
8. 禁止依赖。
9. 边界风险。
10. 后续工作流建议。

## 设计结论

本工作流应输出“模块边界分析报告”，作为实现前的重要治理文档。

它的重点不是画漂亮结构，而是明确：

```text
哪些代码应该写在哪里，哪些代码不应该写在哪里。
```

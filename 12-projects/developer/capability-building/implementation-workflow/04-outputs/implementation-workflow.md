# 代码实现执行工作流

## 目的

在影响范围、风险等级和模块边界已经明确后，指导 AI 稳定完成代码修改。

本工作流重点解决：

1. AI 如何在不扩大范围的情况下实现需求。
2. 如何保护用户已有改动。
3. 如何按模块边界修改代码。
4. 如何同步测试和文档。
5. 如何在实现过程中发现问题并及时停下来确认。
6. 如何输出清晰的交付说明。

一句话：

```text
代码实现执行 = 按已确认的影响范围小步修改、及时验证、清楚交付。
```

## 适用场景

适用于：

- 影响范围已经清楚。
- 风险等级已经明确。
- 模块边界已经清楚。
- 用户已经确认可以进入实现。
- 需要 AI 修改代码、配置、测试或文档。

不适用于：

- 需求仍不清楚。
- 模块边界不清楚。
- 高风险变更尚未获得用户确认。
- 危险变更尚未明确授权。

这些情况应先回到前置工作流。

## 输入要求

至少需要：

- 变更目标。
- 影响范围分析。

建议同时提供：

- 变更风险评估报告。
- 模块边界分析报告。
- 相关文件路径。
- 测试命令。
- 用户明确禁止修改的范围。
- 验收标准。

## 执行原则

### 1. 先保护现场

修改前应查看工作区状态，识别已有改动。

如果发现与本任务无关的用户改动：

- 不回退。
- 不覆盖。
- 不整理。
- 只在必要时绕开。

### 2. 严格控制范围

只修改与本次任务相关的文件。

不要顺手重构、顺手改风格、顺手清理无关代码。

### 3. 小步实现

优先按以下顺序推进：

```text
读相关文件 -> 确认实现点 -> 小范围修改 -> 局部验证 -> 补测试/文档 -> 总体验证
```

### 4. 发现风险及时停下

实现过程中如果发现：

- 实际影响范围超过预期。
- 需要改数据结构。
- 需要改权限、登录、支付、生产配置。
- 需要大范围重构。
- 需求与现有设计冲突。

应停止继续扩大修改，并向用户说明。

### 5. 验证和交付同样重要

实现完成后必须说明：

```text
改了什么
为什么这样改
验证了什么
没验证什么
剩余风险
后续建议
```

## 执行步骤

### 第 1 步：读取执行输入

确认：

- 变更目标。
- 影响范围。
- 风险等级。
- 模块边界。
- 验收标准。
- 禁止修改范围。

产出：实现前确认摘要。

### 第 2 步：检查工作区状态

检查是否存在未提交或用户已有改动。

处理原则：

- 只识别，不回退。
- 涉及同一文件时谨慎合并。
- 无关文件不动。
- 如果已有改动导致无法安全修改，先说明阻塞。

产出：工作区状态摘要。

### 第 3 步：读取相关文件

基于影响范围读取：

- 确定影响文件。
- 关键调用链文件。
- 相关测试文件。
- 相关配置或文档。

产出：实现上下文摘要。

### 第 4 步：制定轻量实现计划

根据风险等级决定计划粒度：

| 风险 | 计划要求 |
| --- | --- |
| 低风险 | 简短说明后可直接改。 |
| 中风险 | 列出修改步骤和验证方式。 |
| 高风险 | 必须先等用户确认方案。 |
| 危险变更 | 默认不执行。 |

产出：实现计划。

### 第 5 步：执行代码修改

执行时遵守：

- 优先复用现有模式。
- 不引入不必要依赖。
- 不破坏模块边界。
- 不扩大影响范围。
- 不覆盖用户无关改动。
- 保持命名、风格和结构一致。

产出：代码变更。

### 第 6 步：补充测试和文档

根据影响范围补充：

- 单元测试。
- 集成测试。
- 端到端测试。
- README。
- API 文档。
- 架构或模块文档。
- 变更说明。

产出：测试和文档变更。

### 第 7 步：执行验证

按项目实际情况运行：

- 格式检查。
- 类型检查。
- 单元测试。
- 构建。
- 手动验证说明。

如果无法运行，应说明原因。

产出：验证结果。

### 第 8 步：输出交付说明

交付说明必须包含：

```text
变更摘要
修改文件
验证结果
未验证内容
风险和注意事项
后续建议
```

## 推荐输出结构

```md
# 实现交付说明

## 变更摘要

## 修改文件

| 文件 | 修改内容 | 原因 |
| --- | --- | --- |

## 验证结果

| 命令或方式 | 结果 |
| --- | --- |

## 未验证内容

## 风险和注意事项

## 后续建议
```

## 快速启动话术

```text
请参考 04-workflows/developer/implementation-workflow.md，
基于已确认的影响范围和风险评估，开始实现这个变更。

变更目标：
【粘贴需求或变更说明】

请先检查工作区状态，保护已有用户改动，然后按最小范围修改代码，完成后运行必要验证，并输出实现交付说明。
```

## 质量要求

- 修改前必须检查相关上下文。
- 不得覆盖用户已有无关改动。
- 不得扩大影响范围。
- 必须遵守模块边界。
- 必须说明验证结果。
- 不能运行的验证必须说明原因。
- 交付说明必须清楚列出修改文件和剩余风险。

# 输入分析

## 核心问题

AI 进入代码实现阶段后，常见失控点是：

- 没看工作区状态，覆盖用户改动。
- 顺手重构无关代码。
- 改动范围超出影响分析。
- 没有遵守模块边界。
- 改完没有测试。
- 无法验证却不说明。
- 交付时只说完成，不说改了什么和风险。

因此，实现工作流不是教 AI 如何写某种语言的代码，而是规定 AI 写代码时的执行纪律。

## 与前后工作流的关系

| 阶段 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `impact-analysis-workflow.md` | 提供确定影响文件和建议实现顺序。 |
| 前置 | `change-risk-assessment-workflow.md` | 提供风险等级和确认策略。 |
| 当前 | `implementation-workflow.md` | 执行代码、测试和文档修改。 |
| 后续 | `testing-verification-workflow.md` | 对测试和验收做专项验证。 |
| 后续 | `documentation-sync-workflow.md` | 对文档变更做专项同步。 |
| 后续 | `code-review-workflow.md` | 对实现结果做质量评审。 |

## 必须覆盖的能力

1. 实现前确认。
2. 工作区状态检查。
3. 上下文读取。
4. 轻量实现计划。
5. 代码修改。
6. 测试和文档变更。
7. 验证执行。
8. 交付说明。

## 设计结论

本工作流应输出“实现交付说明”。

它要回答：

```text
改了什么？
为什么这么改？
有没有超出范围？
验证了什么？
没验证什么？
还剩什么风险？
```

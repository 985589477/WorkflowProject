# 输出评审

## 总体结论

本次“代码评审工作流”可以作为 developer-kit 第二阶段的收口能力。

它要求 AI 以评审者视角优先发现问题，并覆盖需求符合度、正确性、模块边界、风险控制、测试覆盖、文档一致性和可维护性。

## 分项评分

参考 `11-evaluations/output-scorecards/code-review-scorecard.md`。

| 维度 | 分数 | 说明 |
| --- | --- | --- |
| 问题优先 | 5 | 明确要求先列问题，并按严重程度排序。 |
| 范围检查 | 5 | 覆盖超出影响范围、禁止区域、遗漏文件和无关重构。 |
| 需求符合度 | 5 | 覆盖需求目标、验收标准、不做范围和异常流程。 |
| 正确性 | 5 | 覆盖逻辑、边界条件、错误处理、空值、异常和并发。 |
| 模块边界 | 5 | 覆盖模块职责、依赖方向、数据和状态归属。 |
| 风险控制 | 5 | 覆盖风险策略、确认记录和未说明风险。 |
| 测试文档 | 5 | 覆盖测试、未验证内容和文档一致性。 |
| 交付判断 | 5 | 要求基于问题和验证结果给出交付结论。 |

总分：40 / 40。

## 主要优点

- 明确采用问题优先的代码评审方式。
- 评审范围覆盖代码、测试、文档和风险。
- 能作为交付前最后一道质量闸门。
- 能衔接 AI 协作复盘，将问题反哺规则。

## 需要注意

- 实际使用时需要结合真实 diff 或修改文件。
- 不能把个人偏好当成阻塞问题。

## 是否建议提升为全局能力

建议提升。

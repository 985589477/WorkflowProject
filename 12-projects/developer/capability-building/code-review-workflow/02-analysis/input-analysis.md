# 输入分析

## 核心问题

代码实现、测试和文档同步完成后，仍然可能存在：

- 需求没有真正满足。
- 改动超出范围。
- 模块边界被破坏。
- 逻辑 bug 或边界条件遗漏。
- 测试不足。
- 文档与代码不一致。
- 高风险变更没有确认记录。
- 交付结论过于乐观。

因此，代码评审需要作为交付前的最后质量闸门。

## 与前后工作流的关系

| 阶段 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `implementation-workflow.md` | 提供实现结果。 |
| 前置 | `testing-verification-workflow.md` | 提供验证结果。 |
| 前置 | `documentation-sync-workflow.md` | 提供文档同步结果。 |
| 当前 | `code-review-workflow.md` | 对代码、测试、文档和风险做最终评审。 |
| 后续 | `ai-collaboration-retrospective-workflow.md` | 将评审发现的问题沉淀为规则。 |

## 必须覆盖的能力

1. 问题优先。
2. 范围检查。
3. 需求符合度。
4. 正确性。
5. 模块边界。
6. 风险控制。
7. 测试与验证。
8. 文档一致性。
9. 可维护性。
10. 交付判断。

## 设计结论

本工作流应输出“代码评审报告”。

它要回答：

```text
这次变更还有什么问题？
这些问题是否阻塞交付？
如果没有明显问题，还剩哪些测试缺口和风险？
```

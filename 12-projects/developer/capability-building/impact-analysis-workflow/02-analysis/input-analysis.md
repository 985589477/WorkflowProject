# 输入分析

## 核心问题

在真正开始实现前，AI 还需要知道：

- 哪些文件确定要改。
- 哪些文件可能要看但不一定改。
- 哪些区域明确不应该动。
- 变更会经过什么调用链。
- 需要补哪些测试。
- 哪些文档需要同步。

如果没有这个清单，AI 容易出现两类问题：

- 改动范围过小，遗漏测试、文档或调用方。
- 改动范围过大，把局部需求扩成全项目重构。

## 与前后工作流的关系

| 阶段 | 工作流 | 关系 |
| --- | --- | --- |
| 前置 | `change-risk-assessment-workflow.md` | 先判断风险和执行策略。 |
| 前置 | `module-boundary-analysis-workflow.md` | 提供模块边界和禁止依赖。 |
| 当前 | `impact-analysis-workflow.md` | 输出实现前具体影响清单。 |
| 后续 | `implementation-workflow.md` | 按影响清单执行代码修改。 |
| 后续 | `testing-verification-workflow.md` | 按测试影响执行验证。 |
| 后续 | `documentation-sync-workflow.md` | 按文档影响同步说明。 |

## 必须覆盖的能力

1. 变更边界。
2. 确定影响文件。
3. 可能影响文件。
4. 无需修改区域。
5. 调用链。
6. 接口影响。
7. 数据与状态影响。
8. 配置与环境影响。
9. 测试影响。
10. 文档影响。
11. 建议实现顺序。

## 设计结论

本工作流应输出“影响范围分析报告”。

它要回答：

```text
进入实现之前，AI 到底准备动哪些地方，为什么动，哪些地方不动。
```

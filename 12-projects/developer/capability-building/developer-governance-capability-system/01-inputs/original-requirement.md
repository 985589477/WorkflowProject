# 原始需求

## 背景

用户希望建设开发角色能力，但核心目标不是简单让 AI 写代码，而是让 Codex、Cursor 等 AI 开发工具能更好地协作管控项目开发。

当前关注点包括：

- 新项目启动时，AI 应该告诉用户需要补哪些基础文件和规范。
- 产品需求传入后，AI 应该知道如何转成开发结构和模块划分。
- 模块和模块之间的能力边界需要清晰。
- 模块之间的协作交互需要明确。
- AI 需要知道什么时候应该新增模块，什么时候不应该新增模块。
- AI 需要知道模块开发结构如何组织。
- 需要避免文档规则过度限制 Codex 或 Cursor 的工程能力。
- 希望通过 skill、Cursor rules、AGENTS.md 等方式，让不同 AI 工具都能遵守同一套开发治理方法。

## 用户核心表达

用户希望做的是：

```text
一个可以很好与 Codex 或 Cursor 协作的开发模式。
核心目标是通过 skill 管理好整个项目。
在启动一个新项目时，能够告诉我应该添加什么、执行什么项目规范与设计规范。
让 AI 最大限度维护好当前项目而不至于失控。
```

进一步补充：

```text
还需要考虑项目结构建设。
产品需求给过来以后如何做。
每个模块和模块之间的边界划分。
模块和模块之间如何协作交互。
怎么让 AI 清晰理解模块能力边界。
什么时候需要增加新模块。
模块开发结构应该怎么定义。
```

## 本项目目标

建设 developer-kit 的开发治理能力体系第一版，明确：

- developer-kit 管什么。
- developer-kit 不管什么。
- 如何与 Codex / Cursor 协作。
- 新项目启动时检查什么。
- 已有项目接手时检查什么。
- 产品需求如何进入开发治理流程。
- 模块边界如何定义。
- 新增模块如何判断。
- 风险如何分级。
- 后续需要建设哪些细分工作流。

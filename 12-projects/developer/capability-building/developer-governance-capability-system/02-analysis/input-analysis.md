# 输入分析

## 需求本质

本项目不是建设普通“开发提示词”，而是建设一套 AI 协作开发治理体系。

它的目标不是替代 Codex 或 Cursor 的工程能力，而是给这些工具提供：

- 项目接手方法。
- 架构理解方式。
- 模块边界判断。
- 变更风险控制。
- 开发前置检查。
- 交付验证规则。
- 文档同步与复盘机制。

## 核心问题

AI 参与开发时，常见失控点包括：

| 风险 | 表现 |
| --- | --- |
| 需求未澄清就实现 | 用户一句话需求被直接写进代码 |
| 模块边界混乱 | 方便改哪里就改哪里 |
| 结构持续膨胀 | 文件越来越大，职责越来越杂 |
| 新模块随意增加 | 只是小功能也拆出新模块 |
| 文档不同步 | 代码变了，README、架构图、接口说明没变 |
| 测试缺失 | 改完没有验证核心路径 |
| 项目规则冲突 | 通用 AI 规则覆盖了项目本地规则 |
| 过度流程化 | 小改动也被迫走完整方案流程 |

## developer-kit 的定位

developer-kit 应该是：

```text
AI 协作开发治理标准
```

而不是：

```text
代码生成提示词合集
```

## 与 Codex / Cursor 的关系

| 工具 | 作用 |
| --- | --- |
| Codex | 执行读代码、改代码、跑命令、验证、总结 |
| Cursor | 编辑器内上下文协作、局部代码修改、项目内规则调用 |
| developer-kit | 规定开发协作方式、风险判断、模块边界和交付标准 |

developer-kit 应导出为多种适配形态：

```text
Codex skill
Cursor rules
AGENTS.md
项目 docs 规范
```

## 关键设计原则

1. 提供护栏，不提供铁轨。
2. 先判断任务复杂度，再决定流程深度。
3. 项目本地规则优先于通用 developer-kit。
4. 小任务允许轻量执行。
5. 高风险任务必须先分析并等待确认。
6. 模块边界优先于局部方便。
7. 改代码后必须考虑测试、文档和交付说明。

## 第一版能力边界

第一版不直接建设代码实现工作流，而是先建设治理能力地图。

原因：

- 没有治理地图，代码实现工作流容易变成“看到需求就改代码”。
- 先定义模块边界、风险分级、项目结构和文档同步，后续实现工作流才稳定。
- Codex / Cursor 本身已经具备代码执行能力，developer-kit 的价值在于管住开发决策和项目维护。

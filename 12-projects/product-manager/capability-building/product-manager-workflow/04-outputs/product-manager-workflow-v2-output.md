# 产品经理通用工作流

## 目的

把产品经理相关任务从“模糊想法、零散描述或已有材料”推进到“标准输入、结构化分析、正式提示词、产品输出、质量评审和资产沉淀”。

本工作流重点解决四个问题：

1. 用户只有想法时，也能启动项目。
2. AI 先帮助用户整理标准 input，而不是直接跳到最终输出。
3. 产品输出有清晰的分析、提示词、评审和沉淀链路。
4. 后续可从真实项目中反向沉淀模板、案例和知识。

## 适用场景

适用于产品经理相关任务，包括：

- 需求分析。
- PRD 生成。
- 功能规划。
- 用户反馈整理。
- 竞品分析。
- 版本规划。
- 产品策略判断。
- 验收标准整理。
- 从一个模糊产品想法开始形成可执行文档。

如果任务涉及设计或开发，应先用本工作流明确产品目标、边界、用户场景和验收标准，再进入设计或开发工作流。

## 输入来源

输入可以来自两类情况。

### 情况 A：只有模糊想法

例如：

```text
我想做一个会员系统。
我想优化登录流程。
我想让 AI 帮我写一个 PRD。
```

这种情况下，不要直接生成最终产品文档，应先使用：

```text
06-templates/meta/idea-to-input-generator.md
04-workflows/common/idea-to-input-workflow.md
```

生成标准输入文档。

### 情况 B：已有原始材料

例如：

- 需求说明。
- 会议纪要。
- 用户反馈。
- 竞品资料。
- 数据现象。
- 页面截图。
- 功能草稿。

这种情况下，可以直接将材料放入：

```text
12-projects/{角色}/{项目名}/01-inputs/
```

## 执行步骤

### 第 0 步：想法转输入

输入：

- 用户一句话想法。
- 零散描述。
- 不完整需求。

处理动作：

- 使用 `06-templates/meta/idea-to-input-generator.md`。
- 保留用户原始描述。
- 复述用户真正想做的事。
- 提取已知事实。
- 标记 AI 推断。
- 标记待确认信息。
- 推荐项目角色、项目名和后续工作流。

产出：

```text
12-projects/{角色}/{项目名}/01-inputs/original-requirement.md
```

质量要求：

- 用户明确说过的内容写入事实。
- AI 根据上下文推测的内容写入推断。
- 影响输出质量但未明确的信息写入待确认。
- 不把推断写成事实。

### 第 1 步：确认任务类型

输入：

- 标准输入文档。
- 已有原始材料。

处理动作：

- 判断任务属于需求分析、PRD、功能规划、竞品分析、用户反馈整理、版本规划或混合任务。
- 判断是否需要其他角色参与。
- 判断是否需要先补充问题。

产出：

```text
12-projects/{角色}/{项目名}/02-analysis/task-type.md
```

### 第 2 步：分析产品输入

输入：

- `01-inputs/original-requirement.md`
- 其他原始材料。

处理动作：

- 使用 `04-workflows/common/input-analysis-workflow.md`。
- 提取业务背景。
- 提取目标用户。
- 提取用户场景。
- 提取任务目标。
- 提取约束条件。
- 标记事实、推断和待确认。

产出：

```text
12-projects/{角色}/{项目名}/02-analysis/input-analysis.md
```

### 第 3 步：定义产品目标和边界

输入：

- 输入分析。
- 用户期望输出。
- 待确认信息。

处理动作：

- 明确本次要解决的问题。
- 明确不解决的问题。
- 明确成功标准。
- 明确本次输出文档类型。
- 明确是否允许带着待确认问题继续执行。

产出：

```text
12-projects/{角色}/{项目名}/02-analysis/product-scope.md
```

### 第 4 步：选择或生成产品模板

输入：

- 任务类型。
- 产品边界。
- 当前模板库。

处理动作：

- 如果已有合适模板，直接引用。
- 如果没有合适模板，使用 `06-templates/meta/template-generator.md` 生成初版模板。
- 模板只保留可复用结构，不写入一次性业务细节。

产出：

```text
12-projects/{角色}/{项目名}/03-prompts/template-used.md
```

可沉淀目标：

```text
06-templates/product-manager/
```

### 第 5 步：生成正式提示词

输入：

- 产品模板。
- 标准输入。
- 输入分析。
- 产品边界。

处理动作：

- 使用 `06-templates/meta/prompt-generator.md`。
- 填入具体输入材料。
- 保留待确认问题。
- 明确输出格式。
- 明确质量标准。

产出：

```text
12-projects/{角色}/{项目名}/03-prompts/final-prompt.md
```

### 第 6 步：生成产品输出

输入：

- 正式提示词。

处理动作：

- 让 AI 生成产品文档。
- 对不确定内容标记“待确认”。
- 不编造用户、业务、数据或技术事实。
- 输出结构应可评审、可执行。

产出：

```text
12-projects/{角色}/{项目名}/04-outputs/
```

常见输出包括：

- 需求分析文档。
- PRD。
- 功能清单。
- 用户故事。
- 验收标准。
- 竞品分析。
- 版本规划。

### 第 7 步：评审产品输出

输入：

- 标准输入。
- 正式提示词。
- AI 输出。

处理动作：

- 使用 `06-templates/meta/output-reviewer.md`。
- 检查准确性、完整性、结构性、可执行性、可追溯性和可复用性。
- 判断是否需要补输入、重写提示词或重新生成输出。

产出：

```text
12-projects/{角色}/{项目名}/05-review/output-review.md
```

### 第 8 步：沉淀资产

输入：

- 项目输入。
- 输入分析。
- 正式提示词。
- 产品输出。
- 输出评审。
- 复盘记录。

处理动作：

- 使用 `04-workflows/common/asset-promotion-workflow.md`。
- 判断是否提升为模板、案例、知识或评估方法。
- 避免把一次性业务细节误放入通用资产。

产出：

```text
12-projects/{角色}/{项目名}/06-lessons/promotion-notes.md
```

## 输出结果

一次完整产品经理项目至少应包含：

```text
01-inputs/original-requirement.md   标准输入
02-analysis/input-analysis.md       输入分析
02-analysis/product-scope.md        产品目标和边界
03-prompts/final-prompt.md          正式提示词
04-outputs/                         产品输出
05-review/output-review.md          输出评审
06-lessons/                         复盘和沉淀记录
```

## 质量检查

执行完成后检查：

- 是否保留用户原始描述。
- 是否把事实、AI 推断和待确认信息分开。
- 如果用户只有模糊想法，是否先生成了标准输入。
- 是否明确任务类型。
- 是否说明用户、场景、目标和边界。
- 是否有正式提示词。
- 是否有可评审的产品输出。
- 是否完成输出评审。
- 是否判断是否需要沉淀。
- 是否记录项目痛点和下一步。

## 常见分支

### 分支 A：用户只有一句想法

先使用 `idea-to-input-generator`，不要直接生成 PRD。

### 分支 B：用户有材料但结构混乱

先整理成标准输入，再进入输入分析。

### 分支 C：用户已有清晰需求

可以直接进入输入分析，但仍建议保留标准输入文档。

### 分支 D：待确认问题很多

先输出澄清问题清单。如果用户希望继续，可以在明确“基于假设”的前提下生成初稿。

### 分支 E：任务涉及设计或开发

产品经理先输出目标、边界、用户流程和验收标准，再调度设计或开发角色。

## 使用注意事项

- 本工作流描述产品经理任务流程，不直接替代正式提示词。
- 不要跳过 `01-inputs/`，否则后续难以追溯。
- 不要把 AI 推断当成用户事实。
- 如果用户看不懂过程，执行时应同步使用 `06-templates/meta/explainable-project-runner.md`。
- 第一轮输出不必追求完美，但必须留下输入、分析、提示词、输出、评审和复盘记录。
